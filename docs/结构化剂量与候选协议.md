## 1. 同一份结构化药材数据

```json
{
  "name": "方剂知识示例",
  "herbs": [{
    "herb_id": "herb:药材标识",
    "name": "药名",
    "dosage": {"min": null, "max": null, "unit": "g"},
    "preparation": "",
    "source_ids": [],
    "verification_status": "unverified"
  }]
}
```

- 知识库本草、方剂、生成 Schema、候选版本、最终消息与前端卡片共用该结构。历史字符串药材清单迁移为空剂量、未核验的记录。更早的纯文本示例仅恢复已收录药名用于卡片，保留原始正文，不推断剂量或审批状态。
- `dosage_evidence` 保存原始剂量、结构化范围、单位、炮制、原始数据定位、数据版本、核验状态和核验人员/时间。`/api/knowledge/sources/{source_id}` 可定位公开知识出处，不返回患者信息或核验人员身份。
- 只解析明确的现代 g/mg/ml 数值或范围；复杂描述和古代单位保持空值，不做古今换算。模型缺少出处时必须留空；输出无出处的数值会清空并拒绝当前版本，重新生成与审查。
- 核验检查标识、已收录药名、重复药材、配伍、过敏、来源对应、单位、范围和炮制。审查分别保存 `compatibility_status` 与 `dosage_status`。模型自称 verified 不被采纳。
- 内置种子的剂量全部为 unverified。只有有核验人员、核验时间、适用人群的人工核验来源，且当前画像明确为成人、没有识别到特殊条件时，才可能标记“出处已核验”。患者条件未知时保留未核验。这只是出处与结构对应核验，不能证明当前患者适宜使用。
- 正文方剂段由 `render_plan` 生成，卡片直接读取同一份药材数据。自由正文夹带的剂量/用法继续被拒绝。候选 card 明确标注尚未审查，最终 card 分别展示配伍与剂量状态。
- 审查哈希绑定药名、标识、剂量、单位、炮制、出处与画像。最终提交前重新核对知识证据、当前手填画像和审查哈希；改动后不能沿用原审批。

## 2. MCP 的调用身份

提供四个公共知识工具和 `get_my_patient_profile()`，均有只读声明。画像工具不接收患者 ID，仅返回 constitution、allergies、history；不返回会话、摘要、上传文件，不修改画像。

画像读取要求调用者确实存在、患者与调用者相同，并具有数据库中的 `profile:read`。注册默认授予该权限；升级时对旧账户补一次，重启不会恢复已撤销权限。`profile_access_audit` 保存调用者、患者、传输方式、时间与访问结果。内部他人查询一律拒绝；医生/管理员跨患者工具暂未增加。

### 本地 stdio

在 `backend` 安装 `requirements-tools.txt`，为 MCP 客户端设置环境变量 `QIWEN_MCP_USER_ID`（登录用户的 id），命令为 `python -m app.mcp_server`。未绑定身份或权限被撤销时画像工具拒绝，公共知识工具仍可用。

### HTTP

```powershell
docker compose --profile mcp up --build -d
```

访问 `http://127.0.0.1:28001/mcp`，客户端设置 `Authorization: Bearer <岐问登录 access_token>`。HTTP 身份从 JWT 读取，忽略 stdio 的用户配置；每次画像读取重新检查当前权限。登录 token 过期后需要重新登录。该版本使用手动配置 Bearer token，未实现客户端 OAuth 自动登录流程。

Docker MCP 与 API 共享业务卷及签名配置。独立运行 HTTP 服务时，使用 `python -m app.mcp_server --transport streamable-http --host 127.0.0.1 --port 28001`，并确保 `QIWEN_DATA_DIR` 和 `QIWEN_SECRET_KEY` 与 API 一致；宿主机默认 `.data` 与 Docker 命名卷是不同数据。远程部署需设置实际 issuer/resource 地址并配置 HTTPS。

## 3. 事件和候选生命周期

所有事件包括 `run_id`、`candidate_id`、运行内递增 `sequence`、`type` 和 `payload`。为兼容原 REST 消费者，最终事件暂时保留顶层 done/response/message/trace。

| 事件 | 行为 |
| --- | --- |
| candidate.started | 分配新候选 ID，替换前端候选，清空旧卡片 |
| candidate.delta | 模型 SSE 到达时立即发出；body 通道增量显示，plan_json 通道保存结构生成进度，解析完成后生成卡片 |
| candidate.completed | 发布完整候选正文与结构化 plan，标注未完成审查 |
| review.started | 标注审核中 |
| review.rejected | 保存拒绝版本和理由，前端移除该候选正文与卡片；下一次修正使用新 ID |
| review.approved | 保存该候选审查结果；仍等待最终提交 |
| answer.final | 原子提交最终消息、摘要、最终候选和事件后发布权威答案 |
| run.cancelled / run.failed | 终止运行；前端清理候选、显示停止/失败并拒收迟到事件 |

stage 和 phase 事件也使用同一信封。模型支持 SSE 时直接发送流片段；只返回 JSON 的兼容接口只会在响应完成后发出一次片段，不能算实时模型流。发送过部分片段后发生传输失败会终止该轮，不在同一个候选中重试并拼接另一份正文；未产生片段前仍按配置有限重试。

候选与事件分别保存在 candidates/run_events，归属校验覆盖 `/api/runs/{id}/candidates` 和 `/events`。普通历史只读取最终消息或停止/失败记录，不加载被拒候选。审查重试耗尽后使用新的受限候选并提交不含处方的答复。

停止按钮先冻结前端，再取消该 run_id；后端关闭响应流、停止图节点和重试，不提交成功答复、摘要或画像。断开连接执行相同清理。完成与取消竞争由最终事务决定，已提交的最终消息可以刷新恢复。运行协调器仍为单进程，上游是否停止计算和计费需供应商验证。
