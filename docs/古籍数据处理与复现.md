# 古籍与知识种子：来源、清洗和复现

## 数据范围与来源

本项目于 2026-09-24 从 [gstaryu/LingYi 的 `master` 分支](https://github.com/gstaryu/LingYi)取得以下文件。上游仓库采用 Apache-2.0，许可文本保存在 [`backend/resources/Apache-2.0-LICENSE.txt`](../backend/resources/Apache-2.0-LICENSE.txt)。本项目没有保存上游运行数据库、药典 XLSX 或四部方剂 OCR/提取产物；它们不是这次六部古籍文本的可复现输入。

| 本项目位置 | 对应上游位置 | 用途 |
| --- | --- | --- |
| `backend/resources/classics_source/*.txt` | `TCM_data/*.txt` | 保留上游提供的六部文本，字节不改动 |
| `backend/data_pipeline/base.py`、`cleaners.py`、`chunkers/*.py`、`ingest.py` | `data_pipeline/` 同名文件 | 保留清洗、分书切分与归一化代码 |
| `backend/data_pipeline/seed_knowledge.py` | `data_pipeline/seed_knowledge.py` | 保留手工知识种子的源代码 |
| `backend/resources/classics_segments/*.json` | `storage/chunks/*.json` | 上游已生成的古籍片段，字节不改动 |
| `backend/resources/knowledge_seed.json` | 从 `seed_knowledge.py` 转换 | 33 味本草、22 首方剂、14 条药材禁忌 |

这里的“原始数据”指**上游仓库中最早可获得的文本文件**。上游文件名已经带有“完整清洗版”；本项目没有上游抓取前的网页、扫描件或 OCR 原件，也没有重建上游取得这些 TXT 的过程。TXT 内保留的“中国哲学书电子化计划 / Chinese Text Project”标记用于追溯数字来源；向外再分发时，还应核对[该站来源与使用说明](https://ctext.org/help-us/ens)和上游仓库的授权范围。

## 从文本到片段

`backend/scripts/rebuild_classics.py` 与新文本导入共用 `data_pipeline.ingest.chunk_text`。当前流程按用户指定的结构切分方式接入岐问业务库，按下列顺序处理六个 UTF-8 TXT：

1. `chunk_all_books` 根据 `TCM_FILES` 映射，为每本书选择独立的 `chunkers/` 切分器。
2. 根据各书实际格式识别章节、双换行段落、编号条文或药物条目。`chunk_all_books` 直接调用各书 `chunk`，不会自动调用它们的 `clean` 方法；不能将类中定义了清洗方法等同于已执行。清理统一在下一步完成，保留的 TXT 文件不变。
3. `ingest._normalize_chunks` 去除页面导航/页脚杂质和英文主导的行；丢弃少于 10 字、中文占比低于 30% 或类似目录的片段；超过 500 字的片段按句读继续拆分，同时继承章节元数据。
4. `chunk_all_books` 按正文 MD5 做跨书去重；`save_chunks_json` 保留上游 `id`、`content`、`metadata` 三字段，逐书输出 JSON。此 MD5 只用于处理时判重，并非安全摘要。
5. 岐问启动时由 `app.corpus_seed.seed_bundled_corpus` 读取 JSON，核对书名，通过 `store_chunks` 入库。将 `chapter`、`category` 或 `clause_number` 映射到章节字段，使用 `SHA-256(书名 + 换行 + 正文)` 作为业务库主键。完整元数据写入 `corpus.metadata`，原片段 ID 保存在 `source_chunk_id`；重启只补充缺失元数据，不覆盖原正文、章节或用户自行导入的资料。
6. 向量建索引仍调用岐问自己的 `app.retrieval.index_vectors`，按实际嵌入接口编码正文并写入 Chroma。索引已存在的 ID 只刷新元数据；缺少嵌入配置时不宣称向量入库成功。

长度阈值为约 500 个 Python 字符，按 `。` 以及长句中的 `；，、` 拆分，没有滑动窗口重叠，也没有大模型语义切片。超长无合适标点的文本仍可能超限；这是近似长度策略，不是 token 上限保证。`split_from` 保留拆分来源，当前不自动补充父片段或邻片段。具体入口、过滤规则和验收见[结构切片流程](古籍结构切片流程.md)。

结构化种子由 `rebuild_classics.py` 对 `seed_knowledge.py` 的常量声明进行 AST 解析，只读取 `Herb`、`FormulaComponent`、`Formula`、`Contraindication` 的数据构造式，不运行上游数据库入口或导入其运行依赖。后端启动时把这些字段导入 `herbs`、`formulas` 和 `herb_cautions` 表；原有基础配伍规则单独保留。

## 复现与校验

在项目根目录的 PowerShell 中运行：

```powershell
Set-Location backend
..\.venv\Scripts\python.exe -m scripts.rebuild_classics
```

默认是**只读校验**：从六个 TXT 和知识种子源代码重新计算，并与项目内七个派生 JSON 逐项比较。成功时输出：

```text
Verified 1537 chunks in 6 books, 33 herbs, 22 formulas, 14 cautions
```

若修改清洗规则或原始文本，先记录变更原因，再执行 `..\.venv\Scripts\python.exe -m scripts.rebuild_classics --write` 更新派生 JSON，并运行 `..\.venv\Scripts\python.exe -m pytest -q -p no:cacheprovider`。`--write` 只覆盖派生 JSON，不修改 TXT。原始文件兼容 `书名.txt` 和上游的 `书名_完整清洗版.txt`。`data_pipeline.ingest --mode chroma` 已改为调用岐问的 SQLite 与索引入口，不再导入 `lingyi`；它仍需要配置嵌入接口。混合检索的向量配置另见根目录 README。
