# 安全预审、跨轮风险与画像更新改进计划

日期：2026-09-26；2026-09-27 更新。状态：五阶段方案及后续合并确认弹窗已实现，工程测试和 Mock 服务验收已完成。实际行为、验收结果与真实模型未验证的边界见[安全预审与画像确认](安全预审与画像确认.md)，下文保留原始设计，不代替验收记录。

本计划针对岐问当前自主实现的后端制定，保留现有淡蓝界面、参考页面和问答主流程。改动集中在安全预审的数据、状态与追问闭环；需要在现有界面中增加确认入口时，沿用现有样式。检索记忆的 BM25、向量融合和 rerank 继续保留。

## 1. 现状与目标

| 当前代码中的缺口 | 实际影响 | 改进目标 |
| --- | --- | --- |
| `workflow.py::rule_pre_safety` 用急症词的子串匹配 | “没有胸痛”也会触发胸痛阻断 | 判断具体症状是否被肯定、否定或表达为不确定，处理主体与时间 |
| `preflight.py::deterministic_gate` 遇到否定词就丢弃整句 | 同一句中否定一个风险、肯定另一个风险时可能漏掉后者 | 否定绑定到对应实体，保留其他肯定风险 |
| `pre_safety` 的主要输入是当前消息、附件和手填画像 | “还在哺乳”之后回复“头痛三天”，前一轮风险可能不能持续生效 | 每轮读取当前患者的结构化安全事实和未解决问题 |
| 历史摘要和普通 `pending_context` 未直接形成安全上下文 | 旧资料、当前事件与追问答案不能可靠区分 | 保留原始来源，抽取后区分当前事实、历史线索和待确认冲突 |
| 当前过敏描述只临时合并到本轮 `profile` | 下次会话可能不知道曾经明确提供的过敏信息 | 本轮立即参与审查；用户确认后保存到长期结构化档案 |
| 安全追问使用固定的年龄、孕哺、过敏、用药整段问题 | “不是”“已经结束了”难以绑定问题，确认孕哺后可能反复追问 | 独立安全追问状态，逐项确认，按状态继续或保持受限 |

改进后的原则：**检索找到的历史自述是线索；当前患者的已确认安全事实要直接读取。资料齐全只代表可以重新评估，不代表用药安全。**

## 2. 数据如何表示

先定义一个安全事实结构，规则解析与模型补充都输出同一种结构，避免直接把几段历史拼成一串文字再匹配。

| 字段 | 用途与示例 |
| --- | --- |
| `category`、`entity` | 风险类别和具体对象，例如 `allergy` / `甘草`，或症状 / `胸痛` |
| `subject` | 本人、当前已指定的咨询对象、其他人、未知；不能默认所有提到的症状都属于账号本人 |
| `assertion` | `present` / `absent` / `uncertain`，分别表示肯定、明确否定、不确定 |
| `temporal_scope` | 当前、既往、已结束、未知；采集时间与症状发生时间分开记录 |
| `details` | 原始过敏原名称、反应描述、药品名称等；不在现有药材库中的过敏原也要保留 |
| `source` | 消息或附件 ID、来源会话、原文片段位置、采集时间；所有推断能回到证据 |
| `confirmation` | 当前明确自述、待确认的提取结果、已确认长期事实、已被更正的旧事实 |
| `revision` | 状态版本，用于并发校验、纠错记录与候选方案重新审查 |

`subject` 不等于数据库用户 ID。用户问“我妈妈在吃降压药”时，先确认此次为谁咨询，不把母亲的用药写入本人档案。第一版可支持本人和本会话指定的代问对象；代问对象的长期档案管理不在本次范围。

建议增加以下存储。具体字段在第一阶段定稿后再迁移：

- `thread_safety_state`：会话的患者绑定、安全事实、未解决问题、当前限制、版本。业务数据库作为权威来源；LangGraph 检查点只镜像已提交的状态。
- `patient_safety_facts`：本人已确认的长期事实，保留来源和状态。未确认摘要不直接进入此表成为已确认事实。
- `safety_fact_events`：确认、更正、失效等变更记录。审计日志使用 ID、类别和操作，避免复制整段患者文字到运行日志。

原有手填 `profiles` 字段继续保留。迁移不会把“字段为空”解释成“没有风险”，也不会把旧自由文本直接标为已确认的当前状态。

## 3. 每一轮的新处理顺序

1. 校验用户、会话、附件归属，确认此次咨询对象。
2. 直接加载已确认安全事实和本会话安全状态，保留普通问诊的 `pending_context`。
3. 从当前消息与附件抽取带来源的事实；若存在一个明确待回答的安全问题，将短回答绑定到该问题。
4. 汇总同一患者的信息。历史摘要作为待确认线索；近期原文和已提交安全状态作为跨轮依据，不依赖摘要排序结果保住关键风险。

   已确认关键事实和未解决风险不随普通上下文预算一起截断或压缩丢弃；历史原文按来源读取。信息冲突时不简单采用“最新一句覆盖全部”，先核对对象、时间和具体事实。
5. 处理冲突、否定与时间，生成统一 `SafetyContext`。
6. 执行确定性规则，再执行配置好的模型预审。模型不能放宽程序限制；结构不合法、证据缺失或调用失败时，保持受限或阻断，不因失败放行。
7. 程序选择对应的追问模板和能力范围，输出可继续的问诊、补充问题或受限提示。
8. 成功提交最终答复时，原子保存本轮会话安全状态和待确认建议。取消或失败的运行不提交成功状态。

明确的本轮过敏自述即使尚未保存长期档案，也必须立即参与本轮候选校验。长期保存确认与本轮风险生效是两个动作。

## 4. 追问与限制如何流转

保持现有 `allow / clarify / block` 接口语义，在内部增加安全状态和明确的能力范围。`allow` 仍仅表示允许继续相应流程。

| 内部状态 | 含义 | 后续行为 |
| --- | --- | --- |
| `needs_info` | 存在缺失资料、主体不明、时间不明或互相冲突的信息 | 生成针对性问题，不进入被限制的治疗生成节点 |
| `ready_for_review` | 已回答当前问题，但尚未完成重新预审 | 合并答案，重新运行预审，不直接跳过安全节点 |
| `restricted` | 已确认风险，当前策略要求保持限制 | 可以收集资料或给出经检查的一般信息；停止自动候选治疗，说明需人工核对 |
| `blocked` | 命中现有阻断规则或预审不可用 | 使用程序控制的提示，停止后续治疗生成 |
| `resolved` | 当前预审问题已解决，允许相应后续步骤 | 继续普通问诊；候选仍须独立安全审查 |

先完成状态与策略映射，临床限制标准另行复核；不以本次工程改造自行制定临床放行条件。

安全待追问状态 `safety_pending` 至少保存：问题 ID、患者主体、风险类别、缺失字段、允许的回答形式、已收到的资料、原始主诉和状态版本。

具体行为：

- 一次优先展示一个明确问题；多项资料使用带字段名称的表单或逐项问题。优先级沿用既有阻断规则，其余问题按缺失字段处理。
- “不是”只在存在一个可明确回答的是非问题时绑定；多个问题或自由文本问题下要求进一步说明。
- “已经结束了”需要明确指向孕期、哺乳、用药还是症状，以及相关时间；不能统一视为所有风险消失。
- 用户回答“不知道”或跳过，记录为未知，保持相应限制；提供继续一般信息交流的受限路径。
- 用户确认“仍在哺乳”后，该识别问题完成，进入对应受限状态，不重复询问是否哺乳，也不自动解除限制。
- 突然出现新风险时，先处理新风险，保留原主诉与尚未解决的问题。
- 新话题不能自动清除同一患者的未解决风险；明确切换咨询对象时，分别保存状态，不能把前一个人的资料带到后一个人。

## 5. 分阶段实施与交付

### 阶段一：统一事实结构，修正否定、主体和时间（P0）

改动范围：`preflight.py`、`workflow.py::rule_pre_safety`、结构定义；必要时增加独立的 `safety_context.py`。

工作：

1. 用带实体位置的短句解析替换急症子串匹配和“整句含否定词就删除”的逻辑。
2. 先覆盖明确否定、并列、转折、既往、第三方、疑问、假设等已定义表达；复杂表达标为不确定，不假装规则可以理解所有中文。
3. 同一事实中的双重否定、反复更正、模糊时间保留冲突或未知，发起确认。
4. 保留现有危险配伍、绕过审查等规则，统一使用有效主体和事实证据。
5. 建立输入—抽取事实—触发规则—输出状态的标注样例。

验收：明确否定不触发对应肯定词规则；同句其他肯定风险不丢失；历史或他人信息不直接当成本人当前事实；原有肯定风险阻断用例继续通过。这里的验收不等于对所有自然语言完成临床验证。

### 阶段二：跨轮安全上下文与持久化（P0，依赖阶段一）

改动范围：`db.py`、`memory_load`、`pre_safety`、`run_flow`、`main.py::_save_answer`、运行轨迹。

工作：

1. 新增会话安全状态与长期事实存储，提供可重复执行的升级迁移及旧检查点默认值。
2. 每轮直接读取已确认事实和待解决风险；增加近期原文的安全提取。关键安全事实不走 BM25、向量或 rerank 的筛选通道。
3. 区分事实的有效期与来源时间：过敏更正需显式核对，孕哺和当前用药需要适时重新确认。具体复核时限不随意写死。
4. 历史摘要提供线索，必要时回查原消息；摘要缺少原始来源时保持待确认。
5. 会话安全状态与最终答复在同一成功事务中保存；只恢复已完成运行的状态，取消检查点不成为下一轮依据。
6. 为安全状态与患者画像增加版本；提交时校验版本。画像在生成期间改变，候选必须重新审查或停止提交。

验收：“正在哺乳”后只回复“头痛三天”，风险仍生效；无检索结果也能加载已确认过敏；取消、失败、重启不会形成半提交状态；不同账号和不同咨询对象不串数据。

### 阶段三：完成安全追问闭环（P0，依赖阶段二）

改动范围：`workflow.py` 安全路由、问题模板、状态结构；必要的聊天确认交互与前端接口适配。

工作：

1. `safety_pending` 与普通 `pending_context` 分开保存；安全追问期间保留原始症状。
2. 使用程序字段和模板生成具体问题，替换每次都问年龄、孕哺、过敏、用药的固定长句。
3. 将短回答绑定到问题 ID，合并为新事实后重新预审。
4. 记录已经回答的字段，防止重复追问；重复或无法解析的回答转为明确选项，不凭固定轮数自动放行。
5. 完成 `restricted` 对后续节点的能力限制。不可只隐藏最终正文，必须防止受限候选生成节点被调度。

验收：能展示“问题—答案—状态变化—重新预审”的完整轨迹；孕哺被肯定后不陷入重复询问；“不是”不误回答另一个问题；恢复会话后仍能正确续接。

### 阶段四：确认后更新长期画像（P1，依赖阶段二、三）

改动范围：画像 API、数据库事实与变更记录、画像版本校验、前端确认入口。

工作：

1. 从明确自述生成待保存建议，显示原始过敏原、反应、来源和将写入的内容。
2. 用户确认后保存本人长期事实；支持拒绝、修改、撤销和更正。确认接口需要身份、归属和版本校验。
3. 未知药名、食物或其他过敏原照实保留；无法映射到候选校验库时不得声明已经完成该过敏原的校验。
4. “无过敏”与既有已确认过敏冲突时，要求具体核对，不自动清空已知过敏。
5. 未确认推断不覆盖手填资料。孕哺、停药等时间敏感事实保存变化时间与复核状态。
6. 独立的用户确认 API 可以单独提交；由聊天运行产生的待保存建议只在该运行成功后提交。两条路径分别定义事务和幂等行为。

验收：确认后的过敏跨会话持续生效；未确认建议不成为长期事实；第三方叙述不写本人画像；重复确认幂等；更正有来源和版本；删除与旧版本处理遵守明确的数据生命周期。

### 阶段五：模型补充、回归与上线验收（P1，各阶段也同步测试）

改动范围：模型预审协议、评估数据、测试、文档及运行验证。

工作：

1. 模型接收结构化事实、相关原文和问题状态，返回受约束的判断或补充提取。补充事实必须引用本轮提供的证据；无证据的结果不能写档案。
2. 程序决定公开问题模板和路由；模型不能替换审查规则、私自确认事实或夹带治疗内容。
3. Mock 使用真实确定性解析和状态流转；真实模式分别测试接口故障、格式错误与模型行为，不能用 Mock 结果证明真实模型效果。
4. 扩展单元、多轮集成、权限、迁移、取消及画像并发变化测试；保留并运行现有检索和方剂安全回归。
5. 统计标注集上的对应风险误命中、漏检、错误写档案、重复追问与不合规节点调用，说明样本规模和适用范围。没有真实模型配置时明确报告未验证部分。
6. 更新问答流程、API、预审验收文档及变更记录，写清楚已实现能力、现有限制和复现步骤。

验收：全部工程必测用例通过；受限状态没有进入禁止节点；真实接口是否验证有独立结论；临床规则仍需专家审核，不能以工程测试替代。

## 6. 必须覆盖的测试样例

以下是工程行为预期，不是对文本对应病情作临床结论。

| 输入或多轮场景 | 必须验证的行为 |
| --- | --- |
| “没有胸痛，只有头痛” | 不因明确否认的胸痛触发其肯定词规则；其他检查正常执行 |
| “没有胸痛，但现在呼吸困难” | 否定只作用于胸痛；呼吸困难仍触发现有阻断 |
| “并不是没有胸痛” | 不识别为明确否认；按肯定或待确认处理，不能以否定词跳过 |
| “昨晚胸痛，现在没有了” | 保留既往事件与当前否认，依规则确认或限制；不能抹去昨晚事件后自动放行 |
| “如果出现胸痛会怎么样” | 识别为假设性问题，不自动写入当前症状；有歧义时确认 |
| “我妈妈正在吃降压药” | 核对咨询对象；风险绑定母亲，不能写入本人用药档案 |
| “我在哺乳” → “头痛三天” | 前一轮孕哺事实继续参与本轮预审，不依赖记忆检索命中 |
| 问“目前还在哺乳吗” → “不是” | 绑定唯一问题，保留历史事实，重新评估时间与状态 |
| 同时询问孕哺与过敏 → “不是” | 不猜测否认哪一项，要求明确对象 |
| “还在哺乳” → 对应资料补齐 | 识别问题完成；按风险策略保持相应限制，不反复问同一问题 |
| 已存甘草过敏 → “没有过敏” | 产生冲突核对，不静默删除旧事实 |
| “对花生过敏”或未收录药名 | 保存原始信息并提示校验能力边界，不因为药材库不认识而忽略 |
| 当前明确过敏但未确认长期保存 | 本轮即参与审查；不把未确认建议当作已确认长期档案 |
| 保存建议被拒绝、确认、更正 | 分别验证长期存储、跨会话读取和变更记录 |
| 模型超时、格式错误、伪造证据、提示注入 | 不放宽程序结论，不生成虚构长期事实或治疗内容 |
| 追问期间取消、断开、服务重启 | 不写半提交事实；从最后成功状态恢复 |
| 方剂生成期间画像被另一个页面更正 | 旧版本候选不能按旧画像直接提交 |
| 账号 A 的会话或附件传给账号 B | 拒绝读取、确认和写入，安全状态与事实不泄漏 |
| 升级前画像与检查点 | 迁移可重入，不丢旧资料，不自动把未知标成无风险 |

每个多轮用例都应检查最终正文、数据库事实、问题状态、预审决策和实际执行节点，不能只比较输出中的一句提示。

## 7. 部署、文档与恢复

- 每个可交付阶段完成适用测试后，若修改了前端、后端或运行配置，执行 `docker compose up --build -d`。
- 检查 `docker compose ps` 中前后端健康状态，并访问 `http://127.0.0.1:23000/api/health` 与 `/chat`；报告实际模式和服务版本。
- 在测试账号上验证多轮追问、刷新续接、确认后跨会话读取和取消，再交付。界面维持现有淡蓝风格。
- 迁移前备份业务库与检查点，记录版本。回退旧程序不能删除新增事实；若旧程序无法读取新安全状态，应停止该路径或明确保持限制，不能用旧解析逻辑继续当作安全升级已生效。
